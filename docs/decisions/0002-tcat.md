# ADR 0002: Thread Commissioning over Authenticated TLS (TCAT)

- Status: accepted (2026-11-09): TCAT is **optional**; the transport- and
  TLS-agnostic command engine is in `rs-thread-meshcop` behind feature
  `tcat` (default off); the TLS layer and the BLE adapter are deferred
  (option (b) below)
- Date: 2026-11-09
- Scope: Phase 9 (Thread 1.4 additions), Phase 0 decision "TCAT:
  transport-agnostic engine in `-meshcop`, optional thin BLE adapter crate
  later"

## Context

Thread 1.4.1 chapter 13 defines TCAT: a TCAT Commissioner (typically a
phone app) connects to a TCAT Device over a reliable stream (BLE GATT, or
TCP), runs TLS with mutual X.509 certificate authentication, and sends
TCAT Command TLVs (set the Active Operational Dataset, start / stop the
Thread interface, extract the dataset, decommission, application data).
What the Commissioner may do is decided per command from Thread-specific
X.509 v3 extensions in **both** certificates. TCAT is optional for a
Thread Device; OpenThread implements it behind
`OPENTHREAD_CONFIG_BLE_TCAT_ENABLE` (`src/core/meshcop/tcat_agent.cpp`,
`src/core/radio/ble_secure.cpp`, mbedTLS for TLS and X.509).

### What TCAT requires

- **TLS** (section 13.8): the Device MUST support TLS 1.2 **or** TLS 1.3;
  the Commissioner MUST support both. Cipher suites: at least
  `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` for 1.2,
  `TLS_AES_128_GCM_SHA256` for 1.3. (Not AES-128-CCM-8: OpenThread uses
  CCM-8 only for its datagram (DTLS) certificate mode;
  `SecureTransport::Extension` picks GCM-SHA256 for the stream transport
  that TCAT uses.) The Device is the TLS **server** and MUST request and
  validate the client certificate chain against pre-installed trust
  anchors, check validity dates when it knows the time, and enforce a
  `TCAT_TLS_CONN_TIMEOUT` (60 s) handshake timeout. Optional: RFC 6066
  Maximum Fragment Length (1.2), RFC 8449 record_size_limit (1.3).
  OpenThread pins TLS 1.2 (`mbedtls_ssl_conf_{min,max}_tls_version`).
- **X.509** (section 13.10): end-entity and intermediate certificates with
  ECDSA P-256 / SHA-256 signatures; AKI / SKI matching recommended. Thread
  extensions under `1.3.6.1.4.1.44970`: `.3` TCAT Commissioner
  Authorization (OCTET STRING, >= 5 bytes: header with C flag (bit 0) and
  version (bits 5-7, must be >= 1), then one flags byte per command class:
  Commissioning, Extraction, Decommissioning, Application), `.4` Network
  Name, `.5` Extended PAN ID, `.1` Domain Name, `.2` Thread Version
  (Device only). The Device stores the last Commissioner certificate
  (<= `TCAT_COMM_CERT_SIZE_MAX` = 1024 bytes) after commissioning /
  decommissioning.
- **Commands** (section 13.9): TLVs in the Thread base / extended TLV
  format; command classes by type range (General 0x00-0x1F,
  Commissioning 0x20-0x3F, Extraction 0x40-0x5F, Decommissioning
  0x60-0x7F, Application 0x80-0x9F, CCM 0xA0-0xBF). Mandatory: Get Network
  Name, Disconnect, Ping (<= 512 bytes), Get Device ID, Get Extended PAN
  ID, Present PSKd / PSKc Hash, Request Random Number Challenge, Request
  PSKd Hash, Set Active Operational Dataset, Get Commissioner Certificate,
  Get Diagnostic TLVs, Start / Stop Thread Interface, Get Active
  Operational Dataset, Decommission, Get Application Layers; optional:
  Get Provisioning URL, Present Install-code Hash, Send Application Data
  1-4, Vendor Specific. Responses: Response With Status (status codes
  0x00-0x08, 0x10-0x17) or Response With Payload. Proof-of-possession
  hashes are `HMAC-SHA256(key = secret, challenge || device
  subjectPublicKeyInfo)`.
- **Authorization** (section 13.12.1): a fixed per-command algorithm over
  the Commissioner's and the Device's class flags byte (Access, PSKd,
  Network Name, XPAN ID, Domain, PSKc; reserved bits always fail).
- **Transport** (section 13.7): BLE GATT service `0xFFFB` with
  characteristics C1 (client writes) / C2 (server indications), packets of
  at most min(ATT_MTU - 3, 512) bytes carrying the TLS byte stream;
  advertisement with TCAT TLVs (section 13.5); TCP is allowed as another
  stream transport. TMF `/c/te` (TCAT_ENABLE) re-enables TCAT on a
  commissioned device.

### What the workspace has

- `rs_thread_core::crypto`: AES-CCM*, SHA-256, HMAC-SHA256, HKDF, the TLS
  1.2 PRF, ECDSA P-256 **signing** (`ecdsa`, RustCrypto `p256`), EC-JPAKE.
- `rs-thread-dtls`: DTLS 1.2 with exactly one suite
  (`TLS_ECJPAKE_WITH_AES_128_CCM_8`); its record layer is datagram-based
  (epochs, sequence numbers, replay window) and has no certificates.

### What is missing for TCAT

1. A TLS **server** (stream records, handshake with ECDHE key exchange,
   CertificateRequest, client Certificate + CertificateVerify, Finished),
   for 1.2 or 1.3.
2. AES-128-GCM (not in `rs_thread_core::crypto`).
3. ECDHE P-256 key agreement and ECDSA P-256 **verification** (the `p256`
   crate provides both: features `ecdh`, `ecdsa`; `VerifyingKey`
   verification; no hand-rolled curve arithmetic needed).
4. X.509 parsing and path validation without alloc (DER walk of
   tbsCertificate, issuer/subject matching or AKI/SKI, validity, basic
   constraints / key usage of CAs, signature verification, extension
   extraction).
5. The BLE GATT adapter (C1/C2 framing over a BLE host such as
   `trouble-host`) and the TCAT advertisement.

## Candidate crates

- `der` 0.8 (RustCrypto, cached locally): `no_std`, **borrowed** types work
  without alloc (`SequenceRef`, `OctetStringRef`, `AnyRef`, readers) — a
  safe base for a minimal certificate walker.
- `x509-cert` (RustCrypto): complete X.509 model, but its owned
  `Certificate` (extensions are a `Vec`) needs `alloc`; unusable under the
  no-alloc rule without a borrowed-only variant.
- `p256` 0.14 (already a dependency): `ecdsa` verify, `ecdh`; `no_std`, no
  alloc, constant time.
- `aes-gcm` (RustCrypto): `no_std`, in-place AEAD without alloc.
- `embedded-tls`: `no_std`, no alloc, but a TLS 1.3 **client** only; the
  TCAT Device is the server, so it does not fit (the client side could
  serve a host-side TCAT Commissioner test tool).
- `rustls` 0.23: client and server, TLS 1.2/1.3, `no_std` support **with
  alloc**, needs a crypto provider (`rustls-rustcrypto` is experimental);
  heap use and size rule it out for nRF52-class devices.
- mbedTLS (as OpenThread, e.g. through `esp-mbedtls`): proven, but C, and
  against the pure-Rust objective.

## Options

### (a) Full TCAT now (TLS server + X.509 + engine + BLE adapter)

TLS 1.3 server only (allowed for a Device; smaller and simpler than 1.2:
one key schedule over the existing HKDF, no renegotiation / resumption /
RSA, one suite `TLS_AES_128_GCM_SHA256`, one group secp256r1, one
signature scheme `ecdsa_secp256r1_sha256`) on `p256` + `aes-gcm`, plus a
borrowed-only X.509 chain validator on `der`.

- \+ Complete feature; interoperable with every TCAT Commissioner (they
  MUST support 1.3).
- − ~2.5-3.5 kLOC of new security-critical protocol code (TLS 1.3
  server ~1.5-2 kLOC, X.509 validation ~0.8-1.2 kLOC) plus the BLE
  adapter; needs RFC 8448-style vectors, interop against OpenSSL /
  mbedTLS clients and an independent review. Estimate: 4-6 weeks.
- − Uses no hand-rolled primitives, but is a second hand-written
  (D)TLS state machine to audit.

### (b) Engine now, TLS layer later (chosen)

Implement the transport- and TLS-agnostic part in `rs-thread-meshcop`
(feature `tcat`, default off): TLV codec, command classes, the section
13.12.1 authorization algorithm against abstract certificate claims
(the authorization / name / XPAN ID / domain extensions handed over by the
TLS layer after it validated the chain), all command handlers through an
environment trait, proof-of-possession hashes with the existing
HMAC-SHA256 and constant-time comparison, link state. A
`TcatSecureTransport` trait is the seam a future TLS layer (option (a)
in its own crate, e.g. `rs-thread-tls`) or a platform TLS (mbedTLS on a
host, a vendor SDK) implements.

- \+ No new crypto and no new TLS code now; the security-relevant
  authorization logic is testable in isolation with a fake transport.
- \+ Lets a product with a platform TLS stack ship TCAT early.
- − TCAT is not usable on a pure-Rust device until the TLS layer exists.
- Effort: ~1 kLOC with tests (done with this ADR).

### (c) Defer TCAT entirely

- \+ No effort. − Nothing reusable; Thread 1.4 devices commissioned over
  BLE would need OpenThread.

## Decision

Option (b). TCAT is optional for Thread 1.4.1 and for rs-thread. The
engine (`rs_thread_meshcop::tcat`, feature `tcat`) follows the spec where
OpenThread lags it (status codes `Invalid State` (0x08), reserved
authorization bits, Domain Name matching, the PSKc exception for Set
Active Dataset, header version check, Application class numbering of
1.4.1); the deviations are listed in `RSTHREAD-OPENTHREAD-DIFFERENCES.md`.
The TLS 1.3 server + X.509 validator (option (a)) is a later, separately
reviewed crate; the BLE GATT adapter (C1/C2, advertisement) is a thin
crate on top of a BLE host; `/c/te` (TCAT_ENABLE) belongs to the stack
integration.

## Consequences

- `TcatSecureTransport` must be implemented by the TLS layer: it reports
  the validated peer certificate's claims and DER, the device's own
  claims and subjectPublicKeyInfo (for the proof-of-possession hashes),
  carries application data and closes the link. The TLS layer, not the
  engine, enforces chain validation, validity dates and the 60 s
  handshake timeout.
- Security review items: the authorization algorithm, the hash
  verification (constant time, challenge handling), secret hygiene of the
  PSKd / PSKc / install code, the "complete dataset at link start" rule
  for Set Active Dataset, and the Decommission path.
