# Differential tests against OpenThread

`crates/rs-thread-difftest` feeds the same inputs to OpenThread and to
rs-thread and compares the outputs byte for byte (or semantically where
OpenThread intentionally differs; each such case is classified in the test and
listed below). The OpenThread side is OpenThread's own C++ classes, called
through a small shim.

## How it works

- `tools/openthread-sys` builds OpenThread (simulation platform) with cmake and
  ninja as before. With the cargo feature `diff-shim`, `build.rs` also compiles
  `tools/openthread-sys/shim/diff_shim.cpp` with exactly the compiler flags
  ninja uses for the OpenThread core (same defines, same include paths, so the
  internal classes have the layout of the linked library) and links the result
  in front of the OpenThread libraries.
- The shim exposes `extern "C"` functions that take byte buffers or
  fixed-layout structs and return byte buffers (the layouts are mirrored in
  `crates/rs-thread-difftest/src/ffi.rs`). It creates one `ot::Instance`
  (`otInstanceInitSingle`) per test process; `ffi::lock()` serializes the tests
  (OpenThread's instance is not thread safe) and changes into a scratch
  directory first (the simulation platform writes its flash file to `./tmp`).
- Inputs are generated by a seeded SplitMix64 generator, so a failing case
  reproduces. The number of random cases per test is `OPENTRUST_DIFF_CASES`
  (default: a few thousand, see the table).

## Running

```sh
# Default: every test prints "skipped" and passes, nothing from OpenThread is built.
cargo test -p rs-thread-difftest

# Build OpenThread (cmake, ninja; sources in the submodule or $OPENTHREAD_SRC)
# and compare. About 10 s once OpenThread is built.
cargo test -p rs-thread-difftest --features ot

# Long run: 300 000 random cases per test.
OPENTRUST_DIFF_CASES=300000 cargo test -p rs-thread-difftest --features ot --release
```

`cargo test --workspace --exclude openthread-sys` does not build OpenThread: the
`ot` feature is off.

## Coverage

Case counts are those of a default run (`OPENTRUST_DIFF_CASES` unset).

### Crypto and key derivation (`tests/crypto.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `aes_ccm_matches` | CCM* ciphertext and tag for random key, nonce, AAD (0 to 47 bytes), payload (0 to 1199 bytes) and tag length (4 to 16); OpenThread decrypts what we encrypted and vice versa | 3000 |
| `frame_security_levels_match` | MAC nonce, ciphertext and MIC of `seal_frame` for security levels 4 to 7 | 1500 |
| `mle_nonce_matches` | MLE nonce | 500 |
| `thread_keys_match` | MLE key and MAC key for random network keys and key sequences (edge values included), and the previous / next MAC key | 1005 |
| `trel_key_matches` | TREL key | 1000 |
| `hkdf_hmac_sha256_match` | HKDF-SHA-256, HMAC-SHA-256 and SHA-256 for random lengths | 1500 each |
| `kek_derivation_matches` | KEK from the DTLS key block (SHA-256) and from the master secret (TLS 1.2 PRF, reference composed of OpenThread's HMAC) | 500 |
| `pbkdf2_cmac_matches` | PBKDF2 with AES-CMAC-PRF-128, random password, salt (up to 30 bytes), iteration count (even) and key length | 600 |
| `pskc_matches` | PSKc of random passphrases, network names and extended PAN IDs (16384 iterations each); accepted passphrase lengths | 40 (+ 7 lengths) |

Differences found: none in the algorithms. Constraints of OpenThread's
implementation that the inputs respect: PBKDF2 asserts on odd iteration counts
and salts over 30 bytes; the TREL key function is only compiled with TREL, so
the shim repeats its body on OpenThread's HKDF class.

### 6LoWPAN (`tests/lowpan.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `compress_and_decompress_match` | `Lowpan::Compress` against `iphc::compress` (identical header bytes and consumed length, same rejection), then both decompress the result (also as a first fragment with a datagram size) | 4000 |
| `decompress_arbitrary_frames_match` | `Lowpan::Decompress` against `iphc::decompress_datagram` for random IPHC frames and mutations of valid ones: same accept / reject decision and datagram | 6000 |

Inputs: random IPv6 datagrams (traffic class, flow label, hop limit, unicast
addresses of every kind: unspecified, link-local, mesh-local, context-based
with prefixes of 16 to 128 bits, multicast in all forms including RFC 3306
unicast-prefix based; Hop-by-Hop, Destination, Routing and Fragment headers;
UDP with all port forms; ICMPv6, TCP, IP-in-IP), random context tables
(up to 4 contexts with the compress flag set or not), random link-layer
addresses (short, extended, absent), frames of 20 to 59 bytes and of 127 bytes
(header depth fallback).

A run of 600 000 cases per test shows the same picture: 0 unexpected
differences. About 7 % of the compress cases and 0.3 % of the decompress cases
fall in the classes below.

OpenThread quirks (all inputs that no Thread device produces; we do not copy
them, our output must round-trip):

- an address in `fe80::/10` but not `fe80::/64` is compressed as link-local, so
  the middle 54 bits are lost;
- a multicast destination `ffxx::` whose bytes 2 to 15 are all zero gets the
  multicast bit set and no address bytes at all (the datagram is corrupted);
- after a header-depth cut-off (the full compression did not fit the frame),
  a Hop-by-Hop header gets the "next header compressed" bit although the UDP
  header behind it stays uncompressed; with IP-in-IP the cut-off point differs;
- a context shorter than 64 bits drops the address bits between the prefix and
  the IID, and a context longer than the prefix of its Network Data entry reads
  the bytes behind the prefix (decompression adds stale bits for multicast
  with such a context);
- with no link-layer address the IID derivation error is ignored and the
  address is compared with an uninitialized IID (compress) or the IID is
  garbage (decompress);
- the IID derived from the link-layer address gets the bits of the context in
  the CID byte applied even for link-local addresses.

Our behaviour differs from OpenThread's identically in these places: see
`OPENTRUST-OPENTHREAD-DIFFERENCES.md`. A trailing PadN of any size is elided as a
whole by both (RFC 6282 allows it only up to 7 octets).

**Bug found and fixed in rs-thread:** a context shorter than 64 bits was used
even when the address had non-zero bits between the prefix and the IID; those
bits were lost (OpenThread has the same flaw). Such a context is now only used
if those bits are zero (commit "6LoWPAN: only use a context shorter than 64
bits ...", regression test `short_context_prefix_only_used_when_gap_bits_are_zero`).

### MAC frames (`tests/mac.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `header_build_matches` | MAC header bytes from `FrameBuilder` and `TxFrame::Info::PrepareHeadersIn` for random frame type (data, MAC command, beacon), version (2003, 2006, 2015), addresses, PAN IDs, security level and key ID mode, sequence suppression, CSL IE, Header Termination IE; OpenThread's headers also parse to the same fields in our parser | 5000 |
| `parse_matches` | all header fields, header, payload and MIC lengths from `Frame::parse` and `Mac::Frame` for built, bit-flipped, truncated and overwritten frames; same accept / reject decision | 8000 |
| `frame_security_matches` | ciphertext and MIC of `seal_psdu` and `ProcessTransmitAesCcm` (levels 5 to 7, key ID modes 1 and 2), and `open_psdu` of OpenThread's output | 4000 |

Differences found: none for well-formed frames. On corrupted frames we are
stricter, and OpenThread only validates what it needs (about 10 % of the
corrupted cases): we reject frame types other than beacon, data, ACK and MAC
command; treat Sequence Number Suppression and IE Present as reserved before
IEEE 802.15.4-2015 and the version value 3 as invalid; reject the reserved
address mode 01; require a terminated header IE list before a payload, a MAC
command identifier after the IEs, and honour Header Termination 1 and the
Frame Counter Suppression bit, which OpenThread does not know. Multipurpose
(wake-up) frames are not compared: the shim's OpenThread build has no
multipurpose frame support. OpenThread encrypts the payload at every security
level (1 to 3 are authentication only) and asserts on level 4; these levels are
not compared (Thread uses level 5).

### MeshCoP datasets (`tests/dataset.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `validation_and_kept_tlvs_match` | accept / reject of random datasets (`Dataset::from_tlvs` against `otDatasetParseTlvs`: framing, per-TLV validity, duplicates) and the values of the TLVs OpenThread keeps (`otDatasetConvertToTlvs`) | 8000 |

Inputs: all known dataset TLVs with valid and invalid values (channel, name,
security policy and channel mask forms), unknown TLVs, duplicates, bit flips,
truncation.

**Bug found and fixed:** OpenThread rejects control characters in network names
(`IsValidUtf8String`); we accepted them. Fixed in `NetworkName::from_bytes`
and the dataset validation (regression tests in `rs-thread-core` and
`rs-thread-meshcop`). Remaining difference: OpenThread's UTF-8 check only looks
at lead and continuation bytes, so overlong encodings and surrogates pass; we
reject them. OpenThread keeps at most 16 bytes of a longer name in its
`otOperationalDataset` (the TLV check accepts any length, as we do).

### Network Data (`tests/netdata.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `entries_and_stable_subset_match` | the on-mesh prefixes, external routes, services and 6LoWPAN contexts OpenThread's public iterators return against `NetworkDataView`; the stable subset (`RemoveTemporaryData`) bytes against `copy_stable` | 5000 (about 8500 comparisons) |

Inputs: random prefix TLVs (prefix lengths 0 to 128, Has Route, Border Router
and Context sub-TLVs), service TLVs (with and without the Thread enterprise
number, several servers), Commissioning Data TLVs, with and without
corruption. OpenThread asserts on structurally invalid Network Data, so only
well-formed data is fed to it; malformed data (about 7 %) is only given to our
code, which must not panic.

**Bugs found and fixed (stable copy):** the Has Route flags byte is now kept as
received (reserved bits included; we cleared them), and a temporary Context
sub-TLV only supplies the context ALOC to Border Router entries in front of
it (OpenThread removes temporary sub-TLVs while walking the prefix; we used the
Context sub-TLV wherever it was). Regression tests
`stable_copy_keeps_has_route_flags_byte` and
`stable_copy_context_aloc_depends_on_sub_tlv_order`.

Remaining differences: OpenThread keeps the bits behind a prefix length in
the stable copy, we zero them (only differs for corrupted input); a Context
sub-TLV longer than its prefix makes OpenThread read the bytes behind the
prefix (corrupted input only); several Context sub-TLVs in one prefix are all
reported by OpenThread, only the first by us (not generated: invalid).

### MLE TLVs (`tests/mle.rs`)

| Test | Compared | Cases |
|------|----------|-------|
| `find_and_typed_reads_match` | finding a TLV in a stream (value or error class, extended TLVs, malformed and truncated streams) and typed reads of the 12 fixed-size unsigned TLVs (Source Address, Mode, Timeout, frame counters, Address16, Link Margin, Version, PAN ID, Supervision Interval, CSL Timeout, XTAL Accuracy), wrong sizes included | 8000 streams, about 100 000 lookups |

**Bug found and fixed:** `Tlv::FindTlv` in OpenThread starts from "not found"
and a truncated TLV ends the walk without changing it, so a wanted TLV behind a
malformed one is reported as not found. `opentrust_core::tlv::find` returned a
parse error. It now returns `NotFound`; existing unit tests of `rs-thread-core`
and `rs-thread-mesh` that expected `Parse` were updated.

## Not covered

- DTLS / EC-JPAKE handshake interop (mbedTLS as peer): milestone M4, not part
  of this crate.
- Typed parsers of the larger MLE TLVs (Route64, Connectivity, Address
  Registration, Link Metrics), the MeshCoP TLV set outside the dataset
  (commissioning, steering data) and CoAP: covered by the ported OpenThread unit
  vectors (`docs/ot-unit-test-port.md`) and the mixed-network tests
  (`rs-thread-sim`), not yet differentially.
- Multipurpose (wake-up) frames and security levels 1 to 4 on the MAC (see
  above).
- Fuzzing with coverage feedback (`cargo fuzz`) is a separate item.
